# 桌面控制台 UI 调研

日期：2026-10-22  
目标：找到适合 Codex 管理工具的桌面产品语言，降低当前界面的 AI 味和信息混杂。

## 参考产品与可借鉴点

### CC Switch

来源：[Provider switching](https://cc-switch.cc/en/tutorials/provider-switching)、[Feature overview](https://cc-switch.cc/en/tutorials/feature-overview)、[Interface guide](https://github.com/farion1231/cc-switch/blob/main/docs/user-manual/en/1-getting-started/1.3-interface.md)

它把 Provider 卡片做成“状态 + 用量 + 主动作”的工作单元。当前生效、路由生效、普通可选状态使用不同颜色和文案；托盘面板只保留高频切换和当前用量。这个模型适合 Codex 的“监听开关 + 自动重试 + 当前账号”组合。

借鉴：

- 卡片内完成主要动作，不让用户在页面间来回找按钮。
- “已配置”“已启用”“正在生效”拆成三个状态。
- 用量区有独立刷新和可信度，不把缓存当实时数据。
- 托盘/菜单栏作为轻量控制面，主窗口作为详细管理面。

### Raycast

来源：[Raycast Settings](https://manual.raycast.com/settings)、[Keyboard shortcuts](https://manual.raycast.com/keyboard-shortcuts)、[A fresh look and feel](https://www.raycast.com/blog/a-fresh-look-and-feel)

Raycast 的核心不是大 Dashboard，而是快速进入、快速搜索、快速执行。设置页提供全局搜索和紧凑模式；菜单栏负责常用入口，主窗口负责完整配置。

借鉴：

- 顶部放全局搜索和快捷动作，而不是放欢迎语。
- 高频操作使用紧凑 action row：监听、自动重试、立即同步。
- 详情通过侧边抽屉展开，避免首页堆满诊断字段。
- 支持键盘：`⌘K` 打开动作菜单，`⌘1..6` 切换模块。

### Little Snitch

来源：[Control Center](https://help.obdev.at/littlesnitch7/controlcenter-overview)、[Network Monitor](https://help.obdev.at/littlesnitch7/monitor-overview)

Little Snitch 将“控制中心”和“详细监视器”分开：控制中心先给当前状态和入口，详细视图再展示时间线、连接对象和诊断。它的价值在于状态信息足够密，但默认不打断用户。

借鉴：

- 菜单栏面板只展示现在是否健康和是否需要处理。
- 事件流使用时间、对象、动作三列，不使用大段解释。
- 监听停止、数据过期和权限缺失都必须是独立状态。
- 复杂详情可通过快捷键或点击状态进入。

### Linear

来源：[New Linear UI](https://linear.app/changelog/2024-03-20-new-linear-ui)、[Latest design refresh](https://linear.app/now/behind-the-latest-design-refresh)

Linear 的重点是信息密度和一致层级：侧边栏稳定、标题栏克制、动作位置固定、非当前内容低对比度。它通过减少装饰来容纳更多真实信息。

借鉴：

- 左侧导航只放模块，不放产品宣传语。
- 页面标题栏固定放状态筛选和动作。
- 颜色只表达状态，不能每块卡片都使用彩色背景。
- 详情、日志和设置使用统一的表格/列表语言。

## 设计决策

### 产品气质

定位为“本地控制中心”，不是 AI 聊天窗口，也不是营销 Dashboard：

- 不使用欢迎式大标题，例如“你的任务现在怎么样？”
- 不使用机器人、星星、渐变光晕、拟人化句子和大量 emoji。
- 使用短标签、状态、时间、对象和动作。
- 信息优先级由位置、字号和对比度表达，而不是靠彩色卡片。

### 主窗口结构

默认窗口：`1120 × 760`，最小：`980 × 620`。

```text
┌────────────────────────────────────────────────────────┐
│ Codex 任务管家      [监听中 ●] [自动重试 ○] 账号  ···  │
├──────────────┬─────────────────────────────────────────┤
│ 总览          │ 当前状态：需要处理                     │
│ 线程          │ ┌─────────────────────────────────────┐ │
│ 告警          │ │ selected model is at capacity       │ │
│ 账号与用量    │ │ gpt-6-astra · Thread … · 2分钟前     │ │
│ 模型          │ │ Codex 内部重试：已耗尽               │ │
│ 设置          │ │ [重试此 turn] [保持关闭]             │ │
│               │ └─────────────────────────────────────┘ │
│               │ 当前任务列表 / 最近事件 / 官方用量       │
└──────────────┴─────────────────────────────────────────┘
```

首页只解决三个问题：现在是否在监听、是否有需要处理的错误、自动重试是否会行动。历史数据和诊断信息下沉到二级页面。

### 顶部控制条

顶部常驻两个真正的开关，而不是隐藏在设置页：

- **监听 Codex**：`开启` / `关闭`，副文案显示监听方式和最近心跳。
- **自动重试**：`开启` / `关闭`，开启后副文案显示“仅容量错误 · 最多 3 次”。

开关使用 macOS 原生风格 toggle，右侧同时显示文字状态。关闭后不能只变灰，要显示具体后果：`不会执行动作，只记录事件`。

### 当前异常卡片

一屏只允许一个主异常卡片。字段顺序固定：

1. 错误状态：`需要处理` / `Codex 正在重试` / `已恢复` / `已忽略`
2. 原始错误：`selected model is at capacity`
3. 解释：`server_overloaded · willRetry=false`
4. 对象：模型、Provider、Thread、Turn
5. 执行路径：`Codex 内部重试` / `新 turn` / `Windows UI` / `macOS UI`
6. 主动作和次动作

不要同时显示四张告警卡、十个解释段落和技术 JSON。原始数据放进“查看原始事件”抽屉。

### 账号与用量卡片

使用 CC Switch 的 Provider 卡片思路，但只保留 Codex 需要的字段：

```text
ChatGPT Pro                    已登录
已用 4% · 周期还剩 6d 18h       官方 rate limit
重置：2026-10-29 09:00          [刷新]
```

若数据不可用，显示具体原因：

```text
用量不可用
当前 app-server 没有返回 rate limit
[重试读取] [查看诊断]
```

不得使用“大数字 + 绿色”暗示数据一定实时。所有数字旁边必须有来源和采集时间。

### 菜单栏 / 托盘面板

参考 CC Switch 和 Little Snitch，菜单栏不是主窗口缩小版，只提供四项：

- 当前状态：正常 / 需要处理 / 监听关闭
- 监听 Codex：开关
- 自动重试：开关
- 打开主窗口 / 立即同步

有严重告警时显示红色状态点；数据过期时显示灰色斜线状态，不使用绿色假装健康。

### 视觉系统

- 背景：macOS 深色窗口灰，不使用大面积渐变
- 卡片：一层面板色，边框低对比度，避免悬浮网页感
- 强调色：蓝色只表示可执行动作
- 绿色：当前正常/已成功
- 黄色：等待/未确认/数据过期
- 红色：失败/阻止/严重告警
- 字体：系统无衬线；Thread ID、错误码、时间使用等宽字体
- 间距：4、8、12、16、24 px；统一行高
- 圆角：6 px 控件，10 px 面板，不使用超大圆角
- 动效：只用于状态变化和抽屉进入，不能持续闪烁

### 组件规范

| 组件 | 作用 | 禁止 |
| --- | --- | --- |
| Toggle | 监听、自动重试、通知等二态设置 | 用彩色卡片代替开关 |
| Status badge | 显示状态和可信度 | 只显示颜色不显示文字 |
| Action row | 一个主动作 + 一个次动作 | 同时放四个同级按钮 |
| Event row | 时间、对象、结果 | 用长段落替代 |
| Detail drawer | 原始错误、协议响应、诊断 | 首页默认展开所有字段 |
| Provider/account card | 当前账号、用量、切换 | 隐藏数据来源 |

## 验收问题

视觉验收不看“像不像 AI”，而看：

- 用户是否能在 3 秒内找到两个开关？
- 用户是否能马上看出“Codex 正在自己重试”还是“管理器可以行动”？
- 是否能区分已启用、正在生效、数据可用？
- 首页是否只剩一个主异常和一个主动作？
- 关闭监听后，是否清楚知道不会继续执行任何动作？
- 菜单栏面板是否能在不打开主窗口的情况下完成日常控制？
